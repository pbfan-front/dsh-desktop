报告将已完成流程与中断流程分开：`completedWorkflowMs` 只统计完成的运行；每项 P50/P95 都带样本数。`activeWorkflowMs` 是工作流确定性步骤的总时长，`checkpointWaitMs` 是方案确认和预览确认等待。`toConfirmPlanMs` 从工作流创建时起算，**不是**用户发消息到方案出现的完整耗时。对于同一轮直接触发工作流的用户消息，`humanPromptAdmissionToWorkflowStartMs` 从宿主 Inbox 接收起算；历史字段 `humanPromptEntryToWorkflowStartMs` 实际从 `user/message` 被持久化并进入模型上下文起算，**不是真正的轮次开始**。`humanPromptQueueWaitMs` 现在必须有 `turn/start` 才计算，即 Inbox 接收至轮次开始；旧记录不会再用“接收至模型上下文”的差值冒充纯排队。

端到端预览指标仅在工作流完成、预览门禁通过、实际页面观察属于当前 Profile，且观察时间落在 Profile 创建之后与验证完成之前时计算。`humanPromptAdmissionToObservedPreviewMs` 从宿主收到用户消息到已观察到可验证页面；`workflowStartToObservedPreviewMs` 从工作流创建起算；`profileCreatedToObservedPreviewMs` 包含用户选择分支等等待；`observedPreviewToVerificationMs` 展示页面观察到门禁完成的间隔。页面观察不是首像素或首次可交互时刻，不能称为“首次预览可用”。所有这些墙钟指标包含人工确认和可能的长时间暂停，不能当作系统纯执行耗时；没有同轮消息时间戳的旧运行保留零样本，不反推用户入口耗时。

`planConfirmationToCreationStartMs` 与 `previewConfirmationToVerificationStartMs` 单列两个检查点完成后、下个确定性步骤开始前的空档。这些时间不在步骤执行耗时里，也不能未经证据直接归因于 Agent 推理。旧完成运行可能包含很长的人工暂停，因此其墙钟 P95 不代表系统性能回归。

## 准确性用例审核门禁

`scripts/fixtures/business-experience-cases.json` 是业务预期断言清单，不是历史运行的自动摘要。每条用例要写清意图、路由、API、Mock 字段、应出现与不应出现的 UI 文案，并标注目标定位方式和业务行为；负向用例可改为指定精确的失败步骤与错误码。新增用例先标 `review.status=candidate`。只有业务预期经人工核对，并填写可追溯的 `review.evidenceRef` 和 `review.reviewedAt` 后，才可改为 `approved`。工作流自身的分析结论不能为自身预期背书。

默认分支和分支切换已有成对评估器；下文脚本可自动采集默认→选中→默认或 A→B→A 的真实浏览器证据。用例须增加 `branchIsolation.requestPath`（实际请求路径，如 `/mock/loanNbr/loanNbr.json`）。默认分支用例在 `branchIsolation.default` 中声明默认场景的 `scenarioId`、`mockFields`、`visibleText`、`absentText`；分支切换用例在 `branchIsolation.alternateProfileId` 和 `branchIsolation.alternate` 中声明另一分支的 Profile ID 及相同四项预期。主用例的字段和文案始终描述工作流新建/复用的分支。两组业务预期仍须人工审核，不能由运行结果倒推出预期。

聚合报告只输出数量与覆盖分类，不输出需求、路由、API、Mock 值或运行 ID。可选择传入运行记录及用例—运行链接文件：
