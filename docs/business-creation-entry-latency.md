# 创建体验分支：直接进入分析入口

## 目标与证据

本条记录新建自定义状态分支的入口开销。后续用户明确“创建合并套餐页的体验分支”应按默认页面数据直接新增，页面类请求改走 [BEA-062 默认数据分支](business-default-data-branch.md)；只有明确业务状态或数据修改才进入本文的分析与方案流程。

2026-10-24 只读汇总本机 67 份历史创建工作流。历史记录混合了开发、人工操作和受控验收，不是同一需求的性能回归集，也不能代表另一台电脑：

| 区间 | 样本数 | 中位数 |
| --- | ---: | ---: |
| 用户消息进入至工作流开始 | 16 | 12,736ms |
| 首个工具调用至创建入口工具调用 | 15 | 5,185ms |
| Runtime 分析 | 47 | 17.06ms |
| Profile 创建步骤 | 18 | 184ms |

独立核对最近的 Harness 事件，4 次样本均先调用 `business_context` 和 `business_workflow_mode`，随后才调用 `business_start_scenario_workflow`；首个工具至创建入口间隔分别为 6,255、4,858、7,149、6,147ms。这些区间包含工具调度、模型响应和网络，不能算作纯推理耗时。

没有 `/loan/fullLoanApply` 的现成工作流样本，所以尚未测得本次基准需求的创建耗时。

## 本轮调整

- 在创建工具描述开头明确：新的创建请求首先调用 `business_start_scenario_workflow`，保留原始 query，由现有入口解析目标和执行只读分析。
- `business_context`、`business_workflow_mode` 保留诊断用途，不作为新建请求的前置检查；入口报错后再按需读取。
- 已有运行的继续请求读取原运行并恢复检查点，避免重复启动。
- 页面歧义仍交给原消歧流程；自定义状态请求不得猜测路由、场景或页面断言。只指定页面的默认数据新增由 BEA-062 处理。

仅修改宿主插件的工具提示，不改变 Runtime 分析、来源复核、方案确认、创建或预览验证协议。提示不能保证模型一定采用调用顺序，也不代表已经获得性能提升。

## 验收与迁移

本轮现有 `test/business-plugin.test.ts` 回归通过（1 项，包含真实工具注册、参数、桥接与原提示契约），插件 Node 语法检查与 `git diff --check` 通过。这些检查不证明模型会遵循提示。自然语言 Agent 复测仍需记录首个业务工具是否直接进入创建入口，以及收到需求至方案可确认的完整时间；用户确认和手动选择分支的等待应单列。

另一台电脑可在 Desktop 仓库运行 `node scripts/report-business-scenario-baseline.mjs`，默认读取 `build/workflow-runs.json`；也可传入实际开发 Profile 的工作流存储路径。报告只输出计时与分类汇总，不输出需求正文、路由、Profile、API 或响应正文。旧记录缺失的计时不会补猜。

迁移文件为 `packages/dsh-desktop-business/index.js`。需要按现有开发/打包流程重新准备插件并启动新进程；本轮未替换活动客户端，也未创建或切换体验分支。回退时删除本轮入口提示并恢复两个诊断工具的原描述即可。
