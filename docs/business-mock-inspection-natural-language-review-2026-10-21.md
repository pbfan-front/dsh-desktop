## 新工具真实使用及发现的问题

Agent 自主调用 `business_inspect_mock_scenario` 两次：

1. 首次只请求根结构，成功返回 847 字节；这是 shape-only，不是字段值或完整配置。
2. 第二次一次请求 17 个路径，超过原 16 个上限，返回 `E_MOCK_INSPECT_INVALID / 422`，没有读文件或返回部分数据。Agent 随后改用 Overlay 行区间读取，另做了路径定位；它没有自行按 16+1 重试。因此不能声称本轮已通过新工具完成关键值复核，或已完全消除大 Mock 文件读取。

与历史相比，额外 full 工作流查询和自写脚本总结减少，但这种减少也可能受新语义检查直接展示批准来源/实际值影响，不能归给结构化读取一项。

另确认更高优先级的上下文缺口：两次的工作流 retry/propose 等回复带有截断标记，约 49931–49933 字符，已不是可解析 JSON。不是持久化工作流本身损坏：对新运行调用实际 compact 函数得到 72399 字符的合法 JSON，其中 context.analysis 与 analyze-target.output 各 34681 字符，且 evidenceId 相同；输出随后被上层截断。后续应去重和严格约束默认工具摘要，保留按需完整证据入口，不能取消来源/质量/最终页面门禁。

## 采样后的有界小修复

不改变字段上限、路径/字节预算或原错误码，只为“路径数量超限”增加可执行诊断：

```json
{
  "code": "E_MOCK_INSPECT_INVALID",
  "recovery": {
    "action": "retry-same-source-in-batches",
    "maxPaths": 16,
    "receivedPaths": 17,
    "requiredBatches": 2,
    "preserveAllPaths": true
  }
}
```

工具提示强调只读必要字段、数量超限时对同一 API/Scenario 分批且不丢路径；完整来源克隆不要求枚举所有附带字段。Runtime 不自动拆批、截断或合并结果，不降低门禁；各批仍是独立文件快照，不构成联合原子证明。

开发客户端重启后，以原失败调用的完整 17 路径受控重放：17 条请求仍 422 且带 recovery；按 16+1 手动发起后均 200，17 个返回字段全部与当前文件独立读取一致，没有创建或调用模型。这只验证诊断与分批能力，不证明 Agent 下一轮会按提示恢复，未回填上面的原自然语言结果。
